**Topic:** Python list comprehensions vs loops — performance and readability  
**Category:** `language-specific`  
**Difficulty:** `intermediate`  
**Language:** `python`  

### Summary
List comprehensions offer a concise and generally faster alternative to traditional for-loops when creating new lists by evaluating an expression for each item in an iterable. Understanding when to choose comprehensions over loops balances execution speed, memory efficiency, and code maintainability.

### Key Points
- List comprehensions are evaluated in C under the hood, making them faster than standard append-based for-loops in CPython.
- Comprehensions improve readability for simple transformations and filtering, but complex nested logic can severely harm readability.
- Unlike loops, list comprehensions create a new list in memory immediately, which can be problematic for very large datasets.
- List comprehensions have a localized loop variable scope in Python 3, preventing variable leakage into the outer namespace.

### Code Example
*Comparing a standard append loop with an idiomatic list comprehension for filtering and transforming data.*

```python
# GOOD: Pythonic and fast list comprehension
squares = [x**2 for x in range(10) if x % 2 == 0]
```

**❌ Common mistake:**
```python
# BAD: Verbose and slower standard for-loop with append
squares = []
for x in range(10):
    if x % 2 == 0:
        squares.append(x**2)
```

### Best Practices
- ✅ Use list comprehensions for straightforward transformations and filtering where the resulting list is the primary goal.
- ✅ Keep comprehensions to a single line with at most one or two clauses; refactor into a standard loop or helper function if it gets longer.
- ✅ Use generator expressions (using parentheses instead of brackets) when working with massive datasets to save memory.

### Interview Questions
**Q:** Are list comprehensions always faster than standard for-loops?  
**A:** Not always. While they are generally faster due to execution in C and avoiding the overhead of function lookups like .append(), the performance difference is negligible for very simple loops, and standard loops may be preferred if complex logic requires helper functions.  

**Q:** How do variable scopes differ between list comprehensions in Python 3 and traditional for-loops?  
**A:** List comprehensions in Python 3 have their own local scope, meaning the loop variable does not leak into the surrounding outer scope. In contrast, traditional for-loops leave the loop variable bound in the outer scope after the loop finishes.

**Topic:** JavaScript async/await vs Promise.all — when to use each  
**Category:** `language-specific`  
**Difficulty:** `intermediate`  
**Language:** `javascript`  

### Summary
Sequential async/await execution pauses execution for each individual promise, resulting in slow waterfalls if tasks are independent. Promise.all allows concurrent execution of multiple promises, significantly reducing total execution time for independent asynchronous operations.

### Key Points
- Using await sequentially inside a loop causes unnecessary blocking when requests are independent.
- Promise.all initiates all promises concurrently and resolves only when all succeed or any fails.
- If any promise inside Promise.all rejects, the entire batch fails fast.
- Combining async/await with Promise.all offers clean syntax alongside optimal performance.

### Code Example
*Fetching multiple independent resources concurrently using Promise.all instead of a sequential await loop.*

```javascript
// GOOD: Fetching independent users concurrently
const ids = [1, 2, 3];
const promises = ids.map(id => fetch(`/api/users/${id}`).then(res => res.json()));
const users = await Promise.all(promises);
```

**❌ Common mistake:**
```javascript
// BAD: Sequential waterfall execution causes unnecessary delay
const users = [];
for (const id of [1, 2, 3]) {
  const res = await fetch(`/api/users/${id}`);
  users.push(await res.json());
}
```

### Best Practices
- ✅ Use sequential await only when subsequent operations explicitly depend on the result of previous ones.
- ✅ Use Promise.all for independent asynchronous operations to maximize concurrency.
- ✅ Use Promise.allSettled if you need the outcomes of all promises regardless of whether some fail.

### Interview Questions
**Q:** What happens if one promise fails inside a Promise.all call?  
**A:** Promise.all immediately rejects with that error, ignoring the successful completion of any other promises in the array (fail-fast behavior).  

**Q:** How can you run asynchronous requests in parallel inside a Array.map loop?  
**A:** Map the array to async function calls (which return promises) and pass the resulting array of promises directly into Promise.all().

**Topic:** SQL JOIN types — INNER, LEFT, RIGHT, FULL with real examples  
**Category:** `databases`  
**Difficulty:** `beginner`  
**Language:** `sql`  

### Summary
SQL JOIN operations allow combining rows from two or more tables based on a related column between them. Understanding the differences between INNER, LEFT, RIGHT, and FULL joins is crucial for fetching accurate datasets and managing missing relational data.

### Key Points
- INNER JOIN returns only the records that have matching values in both tables.
- LEFT JOIN returns all records from the left table, and the matched records from the right table, with NULLs for unmatched right-side rows.
- RIGHT JOIN returns all records from the right table, and the matched records from the left table, with NULLs for unmatched left-side rows.
- FULL OUTER JOIN returns all records when there is a match in either the left or the right table, filling missing sides with NULL.

### Code Example
*Demonstrates fetching departments and their employees using a LEFT JOIN to include departments without employees.*

```sql
-- GOOD: Using LEFT JOIN to ensure all departments are listed even if they have no employees
SELECT d.department_name, e.employee_name
FROM departments d
LEFT JOIN employees e ON d.id = e.department_id;
```

**❌ Common mistake:**
```sql
-- BAD: Using INNER JOIN which completely omits departments that have zero employees
SELECT d.department_name, e.employee_name
FROM departments d
INNER JOIN employees e ON d.id = e.department_id;
```

### Best Practices
- ✅ Always explicitly alias table names (e.g., FROM users u JOIN orders o) to improve query readability and avoid ambiguous column errors.
- ✅ Index foreign key and primary key columns involved in the JOIN conditions to ensure optimal query performance.
- ✅ Be intentional about choosing LEFT versus RIGHT joins; favor LEFT joins for readability as they maintain the primary table on the left side.

### Interview Questions
**Q:** What is the difference between an INNER JOIN and a LEFT JOIN?  
**A:** An INNER JOIN returns only rows with matching values in both tables, whereas a LEFT JOIN returns all rows from the left table and matched rows from the right table, filling in NULLs where no match exists.  

**Q:** How does placing a filter condition in the ON clause differ from the WHERE clause in a LEFT JOIN?  
**A:** Filtering in the ON clause applies the condition before the join takes place (affecting what rows are matched), while filtering in the WHERE clause is applied after the join, effectively turning a LEFT JOIN into an INNER JOIN if it filters out the generated NULL rows.

**Category:** `devops`  
**Difficulty:** `intermediate`  
**Language:** `language-agnostic`  

### Summary
Git merge and rebase are both designed to integrate changes from one branch into another, but they do so in fundamentally different ways. Merge preserves the exact history as a non-destructive operation, whereas rebase rewrites project history by moving or combining a sequence of commits to a new base commit.

### Key Points
- Git merge creates a new 'merge commit' that combines two branching histories together.
- Git rebase replays your feature branch commits on top of the latest main branch, creating a linear history.
- Rebasing eliminates unnecessary merge commits, making git log much cleaner and easier to read.
- Rebase rewrites commit history, which can break collaboration if applied to shared public branches.

### Code Example
*Demonstrates safely updating a local feature branch using rebase versus creating a merge commit*

```bash
# GOOD: Rebase your feature branch on main for a clean linear history
git checkout feature-branch
git fetch origin
git rebase origin/main
```

**❌ Common mistake:**
```bash
# BAD: Rebasing a shared public branch that other team members are actively pushing to
git checkout main
git pull
git rebase feature-branch # This alters shared history and causes merge conflicts for others
```

### Best Practices
- ✅ Always rebase your local feature branches onto the latest main branch before opening a pull request.
- ✅ Never rebase commits that you have already pushed to a shared remote branch unless you are working entirely alone.
- ✅ Use interactive rebase (git rebase -i) locally to squash 'wip' commits into meaningful logical units before sharing code.

### Interview Questions
**Q:** What is the primary difference between git merge and git rebase?  
**A:** Git merge preserves history by creating a dedicated merge commit, while git rebase rewrites project history by moving commits to a new base, resulting in a linear history.  

**Q:** Why is it considered dangerous to rebase commits on a public shared branch?  
**A:** Rebasing changes commit hashes and rewrites history. If other developers have already pulled those commits, their local branches will diverge and become out of sync, requiring painful manual resets.

### Summary
Docker multi-stage builds allow developers to use multiple FROM instructions in a single Dockerfile, where each FROM starts a new stage with a fresh base. This enables you to copy only the necessary artifacts and compiled binaries from heavy build environments into a lean, secure production image, drastically reducing final image size.

### Key Points
- Uses multiple FROM statements to divide the Dockerfile into distinct logical stages.
- Enables copying specific files and directories across stages using the --from=<stage_name> flag.
- Leaves compilers, build caches, and heavy development SDKs behind in intermediate stages.
- Eliminates the need for complex multi-container build scripts or manual host-side build processes.

### Code Example
*Building a lightweight Go application image by separating the build environment from the runtime environment.*

```dockerfile
# Stage 1: Build the binary
FROM golang:1.21 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o myapp

# Stage 2: Minimal production image
FROM alpine:3.18
WORKDIR /root/
COPY --from=builder /app/myapp .
EXPOSE 8080
CMD ["./myapp"]
```

**❌ Common mistake:**
```dockerfile
# BAD: Building and running in the same heavy image containing all SDK tools
FROM golang:1.21
WORKDIR /app
COPY . .
RUN go build -o myapp
EXPOSE 8080
CMD ["./myapp"]
```

### Best Practices
- ✅ Give every build stage an explicit alias using the AS keyword for better readability.
- ✅ Order your Dockerfile layers from least frequently changed to most frequently changed to maximize build cache utilization.
- ✅ Use distroless or alpine base images for the final production stage to reduce the security attack surface.

### Interview Questions
**Q:** How do multi-stage builds help reduce Docker image size?  
**A:** They let you compile code in a heavy environment containing SDKs, and then copy only the final compiled artifact into a clean, minimal runtime image, discarding all intermediate build tools and caches.  

**Q:** How do you reference artifacts from a previous stage in a Dockerfile?  
**A:** You use the COPY command with the --from flag, specifying either the stage index number or its assigned alias name (e.g., COPY --from=builder /app/bin /bin).

### Summary
The useEffect cleanup function is a mechanism returned by a side-effect callback in React that runs before the component unmounts or before the effect runs again. It is essential for preventing memory leaks by canceling active network requests, clearing timers, and removing event listeners.

### Key Points
- The cleanup function runs right before the component unmounts and before re-running the effect due to dependency changes.
- Failing to clear subscriptions or timers causes memory leaks and potential updates on unmounted components.
- Returning a function from useEffect signals to React that this logic must be torn down when stale.
- AbortController is the modern standard for canceling in-flight fetch requests inside useEffect.

### Code Example
*Demonstrates cleaning up an interval timer inside useEffect to prevent memory leaks.*

```javascript
useEffect(() => {
  const timer = setInterval(() => {
    setSeconds(s => s + 1);
  }, 1000);
  return () => clearInterval(timer);
}, []);
```

**❌ Common mistake:**
```javascript
useEffect(() => {
  setInterval(() => {
    setSeconds(s => s + 1);
  }, 1000);
}, []);
```

### Best Practices
- ✅ Always return a cleanup function whenever you create a subscription, timer, or DOM listener inside an effect.
- ✅ Pass an AbortController signal to fetch requests to automatically cancel pending network responses on unmount.
- ✅ Keep dependency arrays accurate so cleanup functions run at the correct lifecycle boundaries.

### Interview Questions
**Q:** When does the cleanup function of a useEffect hook execute?  
**A:** It runs immediately before the component unmounts, and also right before the effect runs again if any dependencies in the dependency array have changed.  

**Q:** How do you prevent a state update on an unmounted component when an async fetch request finishes?  
**A:** You use an AbortController, passing its signal to the fetch call, and then call controller.abort() inside the useEffect cleanup function.

### Code Example
*Using keyof constraints to safely extract a property from an object*

function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {

**Topic:** Binary search — implementation and edge cases  
**Category:** `algorithms`  
**Difficulty:** `beginner`  
**Language:** `python`  

### Summary
Binary search is an efficient logarithmic time algorithm used to find the position of a target value within a sorted array. By repeatedly dividing the search interval in half, it reduces the time complexity from linear to O(log n), making it essential for processing large datasets quickly.

### Key Points
- Requires the underlying collection to be fully sorted beforehand
- Operates in O(log n) time complexity and O(1) space complexity for iterative implementations
- Maintains low and high pointers to restrict the active search space
- Can be adapted for finding lower/upper bounds, rotated arrays, and answer spaces

### Code Example
*Demonstrating safe pointer updates to prevent integer overflow and infinite loops.*

```python
def binary_search(arr, target):
    low, high = 0, len(arr) - 1
    while low <= high:
        mid = low + (high - low) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1
```

**❌ Common mistake:**
```python
def binary_search_bad(arr, target):
    low, high = 0, len(arr) - 1
    while low < high:
        mid = (low + high) // 2
        if arr[mid] < target:
            low = mid
        else:
            high = mid
    return -1
```

### Best Practices
- ✅ Calculate mid using low + (high - low) // 2 to avoid potential integer overflow
- ✅ Define clear invariants for what low and high represent throughout the loop
- ✅ Test edge cases explicitly including empty arrays, single-element arrays, and targets smaller/larger than all elements

### Interview Questions
**Q:** How would you modify binary search to find the first occurrence of a duplicate element?  
**A:** When arr[mid] equals the target, do not return immediately. Instead, record the index and move the high pointer to mid - 1 to search for earlier occurrences on the left side.  

**Q:** What is the time complexity of binary search and why?  
**A:** O(log n) because the search space is divided in half with each iteration, meaning the number of operations grows logarithmically relative to the input size.

**Topic:** Python decorators — how they work under the hood  
**Category:** `language-specific`  
**Difficulty:** `advanced`  
**Language:** `python`  

### Summary
Python decorators are syntactic sugar built on top of first-class functions and closures, allowing developers to modify or enhance function behavior without changing its source code. Under the hood, the '@decorator' syntax translates to assigning the function variable to the result of calling the decorator function with the original function as an argument.

### Key Points
- Functions in Python are first-class objects, meaning they can be passed as arguments, returned from other functions, and assigned to variables.
- A decorator is a callable that takes another function as input, extends its behavior, and returns a new callable function.
- The syntactic sugar '@my_decorator' above a function definition is precisely equivalent to 'func = my_decorator(func)'.
- Preserving original function metadata (like name and docstring) requires using 'functools.wraps' inside the wrapper.

### Code Example
*Demonstrates writing a custom timing decorator that preserves metadata using functools.wraps versus a broken implementation.*

```python
from functools import wraps
import time

def measure_time(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

@measure_time
def compute(n):
    return sum(i for i in range(n))
```

**❌ Common mistake:**
```python
def measure_time(func):
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        return func(*args, **kwargs)
    return wrapper

@measure_time
def compute(n):
    """Calculates sum."""
    return sum(range(n))

print(compute.__name__) # Output: 'wrapper' instead of 'compute'
```

### Best Practices
- ✅ Always apply '@functools.wraps(func)' to the inner wrapper function to preserve original function signatures and documentation.
- ✅ Design decorators to accept arbitrary arguments (*args, **kwargs) so they remain reusable across functions with varying signatures.
- ✅ When creating parameterized decorators (decorators that take arguments themselves), use a three-layer function closure or a class-based approach.

### Interview Questions
**Q:** What does the '@' syntax sugar actually do under the hood in Python?  
**A:** It takes the function defined immediately below it, passes it as an argument to the decorator function, and rebinds the original function name to the return value of the decorator.  

**Q:** Why is 'functools.wraps' necessary when writing decorators?  
**A:** Without it, the decorated function takes on the identity of the inner wrapper function, overwriting its original '__name__', '__doc__', and module attributes, which breaks debugging and documentation generation.
