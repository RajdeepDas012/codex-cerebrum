**Topic:** Node.js event loop — understanding non-blocking I/O  
**Category:** `language-specific`  
**Difficulty:** `advanced`  
**Language:** `javascript`  

### Summary
The Node.js event loop is a mechanism that allows Node.js to perform non-blocking I/O operations despite JavaScript being single-threaded, by offloading operations to the system kernel whenever possible. Understanding its phases (Timers, Pending Callbacks, Poll, Check, Close) is critical for diagnosing performance bottlenecks and managing asynchronous flow.

### Key Points
- Node.js runs JavaScript on a single main thread, using libuv under the hood to handle asynchronous system operations via a thread pool and kernel polling.
- The event loop operates in distinct phases: Timers (setTimeout/setInterval), Poll (retrieving I/O events), Check (setImmediate), and Close callbacks.
- Microtasks (process.nextTick and Promise.then callbacks) execute immediately after the current operation completes, before the event loop advances to the next phase.
- Heavy CPU-bound synchronous tasks block the main thread, freezing the event loop and delaying all pending asynchronous callbacks and timers.

### Code Example
*Demonstrates execution order between process.nextTick, promises, timers, and setImmediate*

```javascript
console.log('1: Start');

setTimeout(() => console.log('4: Timer'), 0);
setImmediate(() => console.log('5: Immediate'));

Promise.resolve().then(() => console.log('3: Promise'));
process.nextTick(() => console.log('2: NextTick'));

console.log('6: End');
```

**❌ Common mistake:**
```javascript
// BAD: Assuming setTimeout(..., 0) always executes before setImmediate regardless of context
setTimeout(() => console.log('Timer'), 0);
setImmediate(() => console.log('Immediate'));
// Inside an I/O cycle callback, setImmediate is guaranteed to run before setTimeout(..., 0).
```

### Best Practices
- ✅ Offload heavy CPU-bound computations to worker threads (Worker Threads API) or external microservices.
- ✅ Prefer asynchronous APIs (fs.promises, streams) over synchronous alternatives (fs.readFileSync) to keep the event loop responsive.
- ✅ Use setImmediate instead of setTimeout(fn, 0) when you need code to run immediately after the current poll phase I/O cycle.

### Interview Questions
**Q:** What is the difference in execution order between process.nextTick() and Promise.resolve().then()?  
**A:** Both are microtasks, but process.nextTick() has its own queue that is always processed completely before the standard Promise microtask queue during the transition between operations.  

**Q:** Why does setImmediate sometimes run before setTimeout(..., 0) and sometimes after?  
**A:** If called from the main module, the order is non-deterministic depending on performance. However, if called inside an I/O cycle callback, setImmediate is reliably guaranteed to execute before setTimeout.

**Topic:** Database indexing — when and how to add indexes  
**Category:** `databases`  
**Difficulty:** `intermediate`  
**Language:** `language-agnostic`  

### Summary
Database indexes are special lookup structures, typically B-Trees, that improve the speed of data retrieval operations on a table at the cost of additional writes and storage space. Proper indexing transforms slow O(N) full table scans into fast O(log N) operations for frequently queried columns.

### Key Points
- B-Trees are the most common index structure, keeping data sorted for efficient range queries and equality lookups.
- Indexes speed up SELECT queries, JOIN operations, and WHERE clause filters significantly.
- Every index adds overhead to INSERT, UPDATE, and DELETE operations because the index must also be modified.
- Composite indexes rely on leftmost prefix matching, meaning the order of columns in the index definition matters.

### Code Example
*Demonstrates creating a targeted composite index matching common query filters versus over-indexing columns.*

```sql
-- GOOD: Creating a composite index for columns frequently queried together
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
```

**❌ Common mistake:**
```sql
-- BAD: Creating individual indexes on every single column without considering query patterns
CREATE INDEX idx_user ON orders (user_id);
CREATE INDEX idx_status ON orders (status);
CREATE INDEX idx_date ON orders (created_at);
```

### Best Practices
- ✅ Analyze slow query logs and use EXPLAIN or EXPLAIN ANALYZE before adding indexes.
- ✅ Keep composite index column order aligned with filtering selectivity and equality checks first, then range queries.
- ✅ Regularly audit and drop unused or redundant indexes to optimize write operations.

### Interview Questions
**Q:** How does a B-Tree index work and why is it preferred over a hash index for general queries?  
**A:** A B-Tree organizes data in a self-balancing tree structure that maintains sorted order, enabling efficient equality lookups as well as range queries (e.g., BETWEEN, >, <). Hash indexes only support O(1) exact match lookups and cannot handle range operations.  

**Q:** What is the leftmost prefix rule in composite indexes?  
**A:** For a composite index on columns (A, B, C), the database can use the index for queries filtering on A, (A, B), or (A, B, C). However, it cannot efficiently use the index if the query only filters on B or C without including A.
