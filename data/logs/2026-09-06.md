## Run #12 — 00:24 UTC

**Topic:** Node.js event loop — understanding non-blocking I/O  
**Category:** `language-specific`  
**Difficulty:** `advanced`  
**Language:** `javascript`  

### Summary
The Node.js event loop is a mechanism that allows Node.js to perform non-blocking I/O operations despite JavaScript being single-threaded, by offloading operations to the system kernel whenever possible. Understanding its phases (Timers, Pending Callbacks, Poll, Check, Close) is critical for diagnosing performance bottlenecks and managing asynchronous flow.

### Key Points
- Node.js runs JavaScript on a single main thread, using libuv under the hood to handle asynchronous system operations via a thread pool and kernel polling.
- The event loop operates in distinct phases: Timers (setTimeout/setInterval), Poll (retrieving I/O events), Check (setImmediate), and Close callbacks.
- Microtasks (process.nextTick and Promise.then callbacks) execute immediately after the current operation completes, before the event loop advances to the next phase.
- Heavy CPU-bound synchronous tasks block the main thread, freezing the event loop and delaying all pending asynchronous callbacks and timers.

### Code Example
*Demonstrates execution order between process.nextTick, promises, timers, and setImmediate*

```javascript
console.log('1: Start');

setTimeout(() => console.log('4: Timer'), 0);
setImmediate(() => console.log('5: Immediate'));

Promise.resolve().then(() => console.log('3: Promise'));
process.nextTick(() => console.log('2: NextTick'));

console.log('6: End');
```

**❌ Common mistake:**
```javascript
// BAD: Assuming setTimeout(..., 0) always executes before setImmediate regardless of context
setTimeout(() => console.log('Timer'), 0);
setImmediate(() => console.log('Immediate'));
// Inside an I/O cycle callback, setImmediate is guaranteed to run before setTimeout(..., 0).
```

### Best Practices
- ✅ Offload heavy CPU-bound computations to worker threads (Worker Threads API) or external microservices.
- ✅ Prefer asynchronous APIs (fs.promises, streams) over synchronous alternatives (fs.readFileSync) to keep the event loop responsive.
- ✅ Use setImmediate instead of setTimeout(fn, 0) when you need code to run immediately after the current poll phase I/O cycle.

### Interview Questions
**Q:** What is the difference in execution order between process.nextTick() and Promise.resolve().then()?  
**A:** Both are microtasks, but process.nextTick() has its own queue that is always processed completely before the standard Promise microtask queue during the transition between operations.  

**Q:** Why does setImmediate sometimes run before setTimeout(..., 0) and sometimes after?  
**A:** If called from the main module, the order is non-deterministic depending on performance. However, if called inside an I/O cycle callback, setImmediate is reliably guaranteed to execute before setTimeout.

## Run #13 — 01:01 UTC

**Topic:** Database indexing — when and how to add indexes  
**Category:** `databases`  
**Difficulty:** `intermediate`  
**Language:** `language-agnostic`  

### Summary
Database indexes are special lookup structures, typically B-Trees, that improve the speed of data retrieval operations on a table at the cost of additional writes and storage space. Proper indexing transforms slow O(N) full table scans into fast O(log N) operations for frequently queried columns.

### Key Points
- B-Trees are the most common index structure, keeping data sorted for efficient range queries and equality lookups.
- Indexes speed up SELECT queries, JOIN operations, and WHERE clause filters significantly.
- Every index adds overhead to INSERT, UPDATE, and DELETE operations because the index must also be modified.
- Composite indexes rely on leftmost prefix matching, meaning the order of columns in the index definition matters.

### Code Example
*Demonstrates creating a targeted composite index matching common query filters versus over-indexing columns.*

```sql
-- GOOD: Creating a composite index for columns frequently queried together
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
```

**❌ Common mistake:**
```sql
-- BAD: Creating individual indexes on every single column without considering query patterns
CREATE INDEX idx_user ON orders (user_id);
CREATE INDEX idx_status ON orders (status);
CREATE INDEX idx_date ON orders (created_at);
```

### Best Practices
- ✅ Analyze slow query logs and use EXPLAIN or EXPLAIN ANALYZE before adding indexes.
- ✅ Keep composite index column order aligned with filtering selectivity and equality checks first, then range queries.
- ✅ Regularly audit and drop unused or redundant indexes to optimize write operations.

### Interview Questions
**Q:** How does a B-Tree index work and why is it preferred over a hash index for general queries?  
**A:** A B-Tree organizes data in a self-balancing tree structure that maintains sorted order, enabling efficient equality lookups as well as range queries (e.g., BETWEEN, >, <). Hash indexes only support O(1) exact match lookups and cannot handle range operations.  

**Q:** What is the leftmost prefix rule in composite indexes?  
**A:** For a composite index on columns (A, B, C), the database can use the index for queries filtering on A, (A, B), or (A, B, C). However, it cannot efficiently use the index if the query only filters on B or C without including A.

## Run #14 — 01:19 UTC

**Topic:** OAuth 2.0 flow — step by step explanation  
**Category:** `security`  
**Difficulty:** `intermediate`  
**Language:** `language-agnostic`  

### Summary
OAuth 2.0 is an authorization framework that enables third-party applications to obtain limited access to an HTTP service. It matters because it decouples authentication from authorization, allowing users to share specific data without exposing their credentials.

### Key Points
- The Resource Owner (user) grants authorization to the Client (third-party app) to access protected resources.
- The Authorization Server authenticates the user and issues an Access Token upon successful consent.
- The Resource Server hosts the protected data and accepts requests containing the Access Token.
- The Authorization Code Grant with PKCE is the industry standard for securing public and single-page applications.

### Code Example
*Exchanging an authorization code for an access token securely via POST request*

```python
import requests

response = requests.post('https://auth.example.com/oauth/token', data={
    'grant_type': 'authorization_code',
    'client_id': 'your_client_id',
    'code': 'auth_code_from_callback',
    'redirect_uri': 'https://app.example.com/callback',
    'code_verifier': 'pkce_verifier_string'
})
token_data = response.json()
```

**❌ Common mistake:**
```python
import requests

# BAD: Passing sensitive client secret and auth code via GET query parameters
response = requests.get('https://auth.example.com/oauth/token?client_secret=secret&code=auth_code')
```

### Best Practices
- ✅ Always use HTTPS for all OAuth endpoints and redirect URIs to intercept interception attacks.
- ✅ Validate the state parameter during the redirect callback to prevent Cross-Site Request Forgery (CSRF).
- ✅ Keep access token lifespans short and utilize refresh tokens securely for extended sessions.

### Interview Questions
**Q:** What is the difference between OAuth 2.0 and OpenID Connect?  
**A:** OAuth 2.0 is an authorization framework that handles access delegation, whereas OpenID Connect (OIDC) is an authentication layer built on top of OAuth 2.0 that verifies user identity and provides user profile data via an ID token.  

**Q:** Why is the Authorization Code flow with PKCE required for Single Page Applications (SPAs)?  
**A:** Because SPAs run entirely in the browser where code cannot be kept confidential, traditional client secrets cannot be stored safely. PKCE introduces a cryptographically random challenge-verifier pair to prevent authorization code interception attacks.

## Run #15 — 05:19 UTC

**Topic:** WebSockets vs HTTP polling — real-time data strategies  
**Category:** `system-design`  
**Difficulty:** `intermediate`  
**Language:** `language-agnostic`  

### Summary
Choosing the correct transport mechanism for real-time applications requires balancing latency, server load, and architectural complexity. HTTP polling repeatedly requests data at intervals, whereas WebSockets maintain a persistent, full-duplex TCP connection for instant bidirectional communication.

### Key Points
- HTTP polling creates a new request-response cycle on every check, generating massive HTTP header overhead and unnecessary server load if data hasn't changed.
- Short polling asks for data at fixed intervals; long polling holds the HTTP connection open until new data arrives or a timeout occurs.
- WebSockets perform a single HTTP handshake, then upgrade the connection to a persistent TCP socket allowing asynchronous message pushing from client or server.
- WebSockets require explicit state management, heartbeat mechanisms (ping/pong) to detect dead connections, and horizontal scaling strategies like Redis pub/sub.

### Code Example
*Demonstrates setting up a resilient WebSocket client with automatic reconnection logic.*

```javascript
function connectWebSocket(url) {
  const ws = new WebSocket(url);
  ws.onopen = () => console.log('Connected');
  ws.onmessage = (event) => console.log('Received:', event.data);
  ws.onclose = () => {
    console.log('Disconnected. Reconnecting in 3s...');
    setTimeout(() => connectWebSocket(url), 3000);
  };
  ws.onerror = (error) => ws.close();
}
```

**❌ Common mistake:**
```javascript
// BAD: Assuming the connection stays alive forever without handling drops or reconnection
const ws = new WebSocket('wss://api.example.com');
ws.onmessage = (event) => updateUI(event.data);
ws.send('Hello'); // Fails immediately if connection isn't open yet
```

### Best Practices
- ✅ Use Server-Sent Events (SSE) instead of WebSockets if data flow is strictly server-to-client and automatic reconnection built into the browser is desired.
- ✅ Implement exponential backoff with jitter for WebSocket reconnection attempts to prevent thundering herd problems after a server outage.
- ✅ Offload WebSocket session state to a distributed broker like Redis when scaling across multiple server instances.

### Interview Questions
**Q:** How do you scale WebSockets horizontally across multiple backend servers?  
**A:** By using a message broker like Redis Pub/Sub or Apache Kafka so that when a message needs to be sent to a specific user, the server currently holding that user's WebSocket connection receives the event via the broker.  

**Q:** What is the difference between HTTP long polling and WebSockets?  
**A:** Long polling closes the HTTP connection after every response and opens a new one, sending full HTTP headers each time. WebSockets keep a single TCP connection open permanently, drastically reducing overhead for frequent messages.
