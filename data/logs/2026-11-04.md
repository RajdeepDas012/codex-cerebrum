### Summary
A lock-free concurrent Bloom Filter leverages atomic bit-vector updates (using word-level compare-and-swap operations) and hazard pointers to allow multiple threads to safely insert elements and query membership without locks. This architecture maximizes throughput in multi-core systems by eliminating lock contention during parallel data inspection and duplicate filtering.

### Key Points
- Utilizes word-level atomic CAS primitives to update distinct bits within a shared bit-vector safely across threads.
- Employs hazard pointer memory management to track thread-safe access and reclamation of underlying filter structures.
- Provides O(k) time complexity for both insertions and approximate membership queries, where k is the number of hash functions.
- Guarantees zero false negatives with a configurable false positive rate determined by bit-array size and hash function count.

import threading

class ConcurrentBloomFilterWord:
    def __init__(self, size_in_words):
        self.words = [0] * size_in_words
        self.lock = threading.Lock() # Conceptual stand-in for atomic word-level CAS

    def add_bit(self, word_index, bit_mask):
        with self.lock:
            self.words[word_index] |= bit_mask

### Best Practices
- ✅ Group multiple adjacent bits into larger word primitives (e.g., 64-bit integers) to minimize cache line bouncing and optimize word-level CAS operations.
- ✅ Pre-allocate the entire bit-vector capacity during initialization to avoid expensive resizing operations during peak parallel ingestion.

### Interview Questions
**Q:** How do you achieve thread-safe bit-setting in a shared array without using heavy mutual exclusion locks?  
**A:** By packing bits into words and using atomic word-level Compare-And-Swap (CAS) loops to apply bitwise OR masks.  

**Q:** Why can standard Bloom filters not support item deletions natively?  
**A:** Because clearing a bit hash position may inadvertently unset a bit shared by another validly inserted element, introducing false negatives.
