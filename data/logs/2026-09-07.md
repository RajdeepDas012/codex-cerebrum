## Run #137 — 02:30 UTC

**Topic:** Implementing shadow DOM encapsulation and CSS scoping in Web Components with native Custom Elements API  
**Category:** `web-dev`  
**Difficulty:** `intermediate`  
**Language:** `javascript`  

### Summary
Shadow DOM provides a way to attach a hidden, isolated DOM tree to an element, ensuring that internal styles and markup do not leak out and external styles do not leak in. This native encapsulation is crucial for building robust, reusable Web Components without relying on third-party frameworks or CSS-in-JS libraries.

### Key Points
- Attaching a shadow root in 'open' mode allows external JavaScript to inspect the internal DOM tree via element.shadowRoot, while 'closed' restricts access.
- CSS styles defined inside a Shadow DOM are completely scoped to that component and will not affect the global document.
- Global styles do not penetrate the shadow boundary by default, except for inherited properties like font-family and color.
- CSS Custom Properties (variables) cross the shadow boundary, enabling controlled theming of encapsulated components.

### Code Example
*Creating a custom element with a shadow DOM and encapsulated styles using native APIs*

```javascript
class UserCard extends HTMLElement {
  constructor() {
    super();
    this.attachShadow({ mode: 'open' });
    this.shadowRoot.innerHTML = `
      <style>
        p { color: navy; font-weight: bold; }
      </style>
      <p>Encapsulated Content</p>
    `;
  }
}
customElements.define('user-card', UserCard);
```

**❌ Common mistake:**
```javascript
class UserCard extends HTMLElement {
  constructor() {
    super();
    // Mistake: Appending directly to this without a shadow root leaks styles globally
    this.innerHTML = `<style>p { color: red; }</style><p>Leaky Content</p>`;
  }
}
customElements.define('user-card', UserCard);
```

### Best Practices
- ✅ Use CSS Custom Properties (--custom-prop) to expose safe styling hooks for consumers of your component.
- ✅ Leverage the ::part() and ::theme() pseudo-elements when you intentionally need to allow external styling of internal shadow DOM nodes.
- ✅ Keep shadow DOM templates lightweight and construct them efficiently using template literals or HTML templates.

### Interview Questions
**Q:** What is the difference between open and closed shadow DOM modes?  
**A:** Open mode allows external JavaScript via element.shadowRoot to access the shadow tree, whereas closed mode returns null, making it inaccessible from outside the component's internal script. Note that closed mode provides obfuscation, not true security.  

**Q:** How can an external stylesheet style elements inside a Shadow DOM?  
**A:** Global styles do not penetrate shadow boundaries. To style internal elements from the outside, the component must explicitly expose styling hooks using CSS Custom Properties or the ::part() pseudo-element.

**Topic:** Implementing secure cookie-based authentication with HttpOnly, SameSite, and CSRF protection in Next.js API routes  
**Category:** `security`  
**Difficulty:** `advanced`  
**Language:** `javascript`  

### Summary
Implement a robust session management system in Next.js using encrypted HTTP-only cookies to mitigate XSS risks, combined with SameSite attribute enforcement and Double Submit Cookie patterns for CSRF protection. This pattern ensures sensitive JWT or session tokens remain completely inaccessible to client-side JavaScript while preserving stateless API verifications.

### Key Points
- Setting HttpOnly, Secure, and SameSite=Strict/Lax flags on authentication cookies to prevent XSS session theft.
- Handling secure token exchange and cookie serialization within Next.js App Router route handlers.
- Implementing the Double Submit Cookie pattern or custom request headers for comprehensive Cross-Site Request Forgery (CSRF) defense.
- Managing seamless token refresh cycles securely via backend-for-frontend (BFF) architectural patterns.

### Code Example
*Setting a secure HTTP-only authentication cookie in a Next.js App Router API route*

```javascript
import { cookies } from 'next/headers';

export async function POST(request) {
  const { token } = await request.json();
  cookies().set('session', token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',
    path: '/',
    maxAge: 60 * 60 * 24 * 7,
  });
  return Response.json({ success: true });
}
```

**❌ Common mistake:**
```javascript
import { NextResponse } from 'next/server';

export async function POST(request) {
  const { token } = await request.json();

```

### Best Practices
- ✅ Always set SameSite=Strict for high-security applications, or SameSite=Lax if cross-site top-level navigation GET requests require authenticated sessions.
- ✅ Encrypt or sign cookie contents if they contain sensitive payloads that might need validation before hitting downstream microservices.
- ✅ Enforce short-lived access tokens combined with securely stored refresh tokens to minimize the window of vulnerability if a session leaks.

### Interview Questions
**Q:** Why is storing JWTs in localStorage considered a security risk compared to HttpOnly cookies?  
**A:** localStorage is fully accessible via client-side JavaScript, meaning any injected Cross-Site Scripting (XSS) payload can easily read and exfiltrate the tokens. HttpOnly cookies cannot be read by JavaScript, protecting them from XSS theft.  

**Q:** Even with SameSite=Strict cookies, how can an application still be vulnerable to CSRF, and how do you prevent it?  
**A:** Browser support edge cases, legacy proxies, or future protocol modifications can sometimes bypass SameSite constraints. Complete defense requires implementing a Anti-CSRF token (such as the Synchronizer Token Pattern or Double Submit Cookie technique) for all state-changing requests.
