**Topic:** Implementing shadow DOM encapsulation and CSS scoping in Web Components with native Custom Elements API  
**Category:** `web-dev`  
**Difficulty:** `intermediate`  
**Language:** `javascript`  

### Summary
Shadow DOM provides a way to attach a hidden, isolated DOM tree to an element, ensuring that internal styles and markup do not leak out and external styles do not leak in. This native encapsulation is crucial for building robust, reusable Web Components without relying on third-party frameworks or CSS-in-JS libraries.

### Key Points
- Attaching a shadow root in 'open' mode allows external JavaScript to inspect the internal DOM tree via element.shadowRoot, while 'closed' restricts access.
- CSS styles defined inside a Shadow DOM are completely scoped to that component and will not affect the global document.
- Global styles do not penetrate the shadow boundary by default, except for inherited properties like font-family and color.
- CSS Custom Properties (variables) cross the shadow boundary, enabling controlled theming of encapsulated components.

### Code Example
*Creating a custom element with a shadow DOM and encapsulated styles using native APIs*

```javascript
class UserCard extends HTMLElement {
  constructor() {
    super();
    this.attachShadow({ mode: 'open' });
    this.shadowRoot.innerHTML = `
      <style>
        p { color: navy; font-weight: bold; }
      </style>
      <p>Encapsulated Content</p>
    `;
  }
}
customElements.define('user-card', UserCard);
```

**❌ Common mistake:**
```javascript
class UserCard extends HTMLElement {
  constructor() {
    super();
    // Mistake: Appending directly to this without a shadow root leaks styles globally
    this.innerHTML = `<style>p { color: red; }</style><p>Leaky Content</p>`;
  }
}
customElements.define('user-card', UserCard);
```

### Best Practices
- ✅ Use CSS Custom Properties (--custom-prop) to expose safe styling hooks for consumers of your component.
- ✅ Leverage the ::part() and ::theme() pseudo-elements when you intentionally need to allow external styling of internal shadow DOM nodes.
- ✅ Keep shadow DOM templates lightweight and construct them efficiently using template literals or HTML templates.

### Interview Questions
**Q:** What is the difference between open and closed shadow DOM modes?  
**A:** Open mode allows external JavaScript via element.shadowRoot to access the shadow tree, whereas closed mode returns null, making it inaccessible from outside the component's internal script. Note that closed mode provides obfuscation, not true security.  

**Q:** How can an external stylesheet style elements inside a Shadow DOM?  
**A:** Global styles do not penetrate shadow boundaries. To style internal elements from the outside, the component must explicitly expose styling hooks using CSS Custom Properties or the ::part() pseudo-element.

**Category:** `security`  
**Difficulty:** `intermediate`  
**Language:** `python`  

### Summary
Webhook signature verification ensures that incoming HTTP requests genuinely originate from a trusted third-party service rather than an attacker. Combined with robust exponential backoff retry mechanisms, this architecture guarantees secure and reliable event-driven integrations.

### Key Points
- Use HMAC-SHA256 with a shared secret to cryptographically validate the payload signature.
- Access the raw request body bytes instead of parsed JSON to avoid serialization discrepancies during signature calculation.
- Employ constant-time comparison (hmac.compare_digest) to prevent timing side-channel attacks.
- Implement exponential backoff with jitter for webhook delivery retries to prevent thundering herd problems.

### Code Example
*FastAPI endpoint verifying HMAC-SHA256 webhook signatures using raw body bytes and constant-time comparison.*

```python
import hmac
import hashlib
from fastapi import FastAPI, Request, Header, HTTPException, status

app = FastAPI()
SECRET_KEY = b"your_secret_webhook_key"

@app.post("/webhook")
async def receive_webhook(request: Request, x_signature: str = Header(None)):
    if not x_signature:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Missing signature")
    
    body_bytes = await request.body()
    computed_signature = hmac.new(SECRET_KEY, body_bytes, hashlib.sha256).hexdigest()
    
    if not hmac.compare_digest(f"sha256={computed_signature}", x_signature):
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="Invalid signature")
    
    payload = await request.json()
    return {"status": "success", "event_id": payload.get("id")}
```

**❌ Common mistake:**

```python
import hmac
import hashlib
from fastapi import FastAPI, Request

app = FastAPI()

    # WRONG: Parsing JSON first alters key order and spacing, breaking the signature
    # WRONG: Using standard '==' string comparison exposes the app to timing attacks

```

### Best Practices
- ✅ Always retrieve the raw request body stream as bytes before any JSON parsing takes place.
- ✅ Utilize `hmac.compare_digest()` to perform timing-safe string comparisons.
- ✅ Include timestamp headers alongside signatures to reject stale requests older than a specific threshold (e.g., 5 minutes).
- ✅ Log delivery failures securely and implement a dead-letter queue for persistently failing webhook endpoints.

### Interview Questions
**Q:** Why must you use the raw request body instead of parsed JSON when verifying a webhook signature?  
**A:** JSON parsers do not guarantee key order, whitespace, or formatting consistency. Comparing a signature generated on the sender's raw payload against a re-serialized JSON dictionary on the receiver's end will result in mismatched hashes.  

**Q:** What is a timing attack in the context of signature verification, and how do you prevent it?  
**A:** A timing attack measures the exact time it takes for an application to reject an invalid signature character-by-character. It is prevented by using constant-time comparison algorithms like `hmac.compare_digest()` that take the same amount of time regardless of where the mismatch occurs.

**Topic:** Implementing optimistic concurrency control in GraphQL mutations with version checking and custom error handling in Apollo Server  
**Category:** `web-dev`  
**Difficulty:** `advanced`  
**Language:** `javascript`  

### Summary
Optimistic concurrency control (OCC) prevents race conditions in distributed applications by validating version numbers before committing updates. By integrating version checks into Apollo Server resolvers and handling custom errors, you can safely handle concurrent edits without locking database rows.

### Key Points
- Requires a version or timestamp column on the database record to track state changes.
- Mutations must accept an expected version argument alongside entity updates.
- Resolvers check if the database version matches the client-supplied version before applying updates.
- Custom GraphQLError objects should be thrown to return structured conflict details to the client.

### Code Example
*Resolving an update mutation with optimistic concurrency control and version incrementing in Apollo Server*

```javascript
const resolvers = {
  Mutation: {
    updatePost: async (_, { id, title, expectedVersion }, { dataSources }) => {
      const post = await dataSources.db.posts.findById(id);
      if (post.version !== expectedVersion) {
        throw new GraphQLError('Conflict: The post has been modified by another user.', {
          extensions: { code: 'CONCURRENCY_CONFLICT', currentVersion: post.version }
        });
      }
      return dataSources.db.posts.update(id, { title, version: post.version + 1 });
    }
  }
};
```

**❌ Common mistake:**
```javascript
const resolvers = {
  Mutation: {
    updatePost: async (_, { id, title }, { dataSources }) => {
      return dataSources.db.posts.update(id, { title });
    }
  }
};
```

### Best Practices
- ✅ Return the newly incremented version number in the mutation response payload so the client can update its local cache.
- ✅ Use distinct GraphQL error extension codes (e.g., CONCURRENCY_CONFLICT) to help client apps trigger a refetch flow automatically.
- ✅ Combine OCC with database-level isolation levels for critical financial or inventory entities.

### Interview Questions
**Q:** How do you handle a concurrency conflict in a GraphQL mutation using Apollo Server?  
**A:** By comparing the client's expected version with the database version in the resolver, throwing a custom GraphQLError with error extensions if they mismatch, and returning the conflict details to the client.  

**Q:** Why is optimistic concurrency control preferred over pessimistic locking in web applications?  
**A:** OCC assumes conflicts are rare, allowing multiple readers to access data without locking database rows, which significantly increases scalability and throughput.
