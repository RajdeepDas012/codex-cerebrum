### Summary
A concurrent Splay Tree is an advanced self-adjusting binary search tree that moves frequently accessed elements closer to the root to optimize lookup times. By combining atomic root-rotation and self-balancing CAS primitives with hazard pointer memory management, it achieves high throughput and lock-free thread safety across multiple cores.

### Key Points
- Utilizes atomic Compare-And-Swap (CAS) operations to execute structural modifications like root rotations safely without global locks.
- Employs hazard pointers to track threads actively reading nodes, safely deferring memory reclamation to prevent use-after-free bugs.
- Self-optimizes by 'splaying' accessed nodes to the root, naturally clustering hot keys for faster subsequent access in cache layers.
- Ensures linearizability across multi-core architectures during concurrent inserts, lookups, and restructuring operations.

function concurrent_rotate_right(node, hazard_mgr):
    while true:
        hazard_mgr.protect(node)
        left_child = node.left
        if left_child == null: break
        hazard_mgr.protect(left_child)
        if node.left != left_child: continue
        
        if atomic_cas(&node.left, left_child, left_child.right):
            if atomic_cas(&left_child.right, left_child.right, node):
                break
    hazard_mgr.clear()

### Interview Questions
**Q:** How do hazard pointers prevent the ABA problem and use-after-free issues in lock-free tree rotations?  
**A:** Hazard pointers allow threads to publish which nodes they are currently accessing so that other threads can defer memory deallocation until no thread holds a reference to those nodes.  

**Q:** Why is it difficult to implement a lock-free splay operation using a single CAS primitive?  
**A:** A splay operation often modifies multiple parent-child pointers across different levels of the tree simultaneously, which exceeds the atomic guarantees of single-word CAS primitives.
