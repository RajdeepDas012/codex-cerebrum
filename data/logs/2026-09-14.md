- Provides extremely high throughput and cache locality by packing allocations contiguously in memory.
- Typically lacks individual deallocation capability, requiring bulk resets or arena lifecycle management to reclaim memory.

### Code Example
*Demonstrates a thread-safe lock-free bump allocation routine using atomic fetch-and-add or compare-and-swap.*

```cpp
#include <atomic>
#include <cstdint>
#include <cstdlib>

class BumpAllocator {
    char* arena;
    size_t capacity;
    std::atomic<size_t> offset;
public:
    BumpAllocator(size_t size) : capacity(size), offset(0) {
        arena = static_cast<char*>(std::malloc(size));
    }
    ~BumpAllocator() { std::free(arena); }
    
    void* allocate(size_t size, size_t alignment = 8) {
        size_t current, next;
        do {
            current = offset.load(std::memory_order_relaxed);
            size_t padding = (alignment - (reinterpret_cast<uintptr_t>(arena + current) % alignment)) % alignment;
            next = current + padding + size;
            if (next > capacity) return nullptr;
        } while (!offset.compare_exchange_weak(current, next, std::memory_order_release, std::memory_order_relaxed));
        return arena + current + padding;
    }
};
```

**❌ Common mistake:**
```cpp
void* allocate(size_t size) {
    size_t current = offset.load();
    offset.store(current + size); // Non-atomic update prone to data races and lost updates
    return arena + current;
}
```

### Best Practices
- ✅ Align allocation requests to hardware cache line sizes or native word boundaries to optimize CPU fetch performance.
- ✅ Pair the allocator with a reset mechanism (like a arena roll-back) to efficiently reclaim all allocated memory at once.

### Interview Questions
**Q:** How do you handle memory alignment in a lock-free bump allocator without introducing race conditions?  
**A:** Calculate the padding needed based on the current offset inside the CAS loop before attempting to atomically update the shared offset pointer with the padded size.  

**Q:** What is the primary limitation of a bump allocator regarding memory reclamation, and how is it typically solved?  
**A:** It lacks individual free operations; memory is usually reclaimed in bulk by resetting the offset counter to zero when an entire task batch or frame completes.

### Summary
An adaptive radix tree (ART) is a space-efficient indexing structure that dynamically changes its internal node sizes (Node4, Node16, Node48, Node256) based on fan-out density. Combining this with optimistic latch coupling and lock-free node growth allows high-throughput concurrent in-memory key-value stores to achieve high read parallelism without global locking overhead.

### Key Points
- Utilizes adaptive node sizing (Node4, Node16, Node48, Node256) to eliminate wasted memory overhead typical of standard radix tries while maintaining high traversal speed.
- Implements optimistic latch coupling by reading version lock counters before and after traversing internal paths, avoiding costly exclusive locks on read-heavy workloads.
- Employs atomic node growth and replacement (such as CAS operations on child pointers) to transition from smaller node types to larger ones dynamically under concurrency.
- Performs path compression (prefix compression) to collapse chains of single-child nodes into compressed byte arrays, drastically reducing memory footprint and tree depth.
